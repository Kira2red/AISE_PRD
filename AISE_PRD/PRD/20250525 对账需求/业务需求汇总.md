# AISE 对账 & 退款管理 — 业务需求汇总

> 整理时间：2026-05-25

---

## 一、背景

AISE 管理后台目前缺少统一的支付对账与退款管理能力，各类查询依赖开发介入，效率较低。同时需要支持用户端退费流程、统一数据统计等业务场景。

---

## 二、支付渠道现状

| 渠道 | 说明 | 当前状态 |
|------|------|----------|
| 微信支付 | 用户自助报名 | 已接入 |
| 支付宝 | 用户自助报名 | 已接入 |
| API 渠道 | 第三方平台通过 API 报名（暂不管） | 待排期 |
| 后台直接开通 | 管理员在后台直接为学员开通报名，不走支付 | 已有能力 |

> 用户报名方式：① 用户在前台自助报名（微信/支付宝） ② 运营后台直接开通

## 三、业务需求清单

### 3.1 对账管理

需求划分三块，可独立推进。核心逻辑：通过「商户交易编号」将 AISE 订单与微信/支付宝流水逐笔匹配。

| 编号      | 模块       | 描述                         | 优先级 |
| ------- | -------- | -------------------------- | --- |
| R-AC-01 | 前台支付对账   | 对账微信、支付宝的用户自助支付订单          | —   |
| R-AC-02 | API 渠道对账 | 对账通过 API 渠道产生的报名订单（暂不管，后续排期） | 低 |
| R-AC-03 | 后台直接开通对账 | 对账管理员后台直接开通的报名记录（无实际资金流，用于统计核对） | — |

### 3.2 退款管理（后台）

| 编号 | 模块 | 描述 |
|------|------|------|
| R-RF-01 | 退款操作 | 后台支持退款操作，原路退回，由最高管理员执行 |
| R-RF-02 | 退款联动 | 退款时可联动执行：撤销考试资格、撤销证书等操作 |
| R-RF-03 | 用户端退费流程 | 见下方 3.3 |

### 3.3 用户端退费逻辑

| 阶段 | 时间范围 | 退费规则 |
|------|----------|----------|
| 阶段 1 | 公开报名阶段 | 用户随时退，无需审核，点击按钮后费用原路退回 |
| 阶段 2 | 报名截止 ~ 正式考试前 | 退费需后台审核，用户提交退费申请 → 运营/财务审核通过后退款 |
| 阶段 3 | 考试开始 ~ 考试结束 | 不支持退费（前端隐藏退费按钮），特殊情况人工处理 |

> 阶段 1 典型场景：用户报错渠道、报错考试等级/考场，需自行取消重报。

### 3.4 数据统计 / 报表

| 编号 | 模块 | 描述 |
|------|------|------|
| R-DT-01 | 报名人数统计 | 按时间段统计总报名人数 |
| R-DT-02 | 渠道报名统计 | 按渠道维度统计报名人数 |
| R-DT-03 | 渠道费用明细 | 各渠道收入/支出明细查询 |
| R-DT-04 | 对账报表 | 统一的对账数据面板，减少开发查询介入 |

### 3.5 角色与权限

| 编号 | 模块 | 描述 |
|------|------|------|
| R-RB-01 | 最高管理员 | 现有最高管理员角色即可操作退款审核、对账查看、财务数据导出等功能，暂不细分财务角色 |
| R-RB-02 | 运营后台直接开通 | 运营可通过后台直接为学员开通报名（现有能力，对账时作为「后台直接开通」渠道统计） |

### 3.6 对账数据设计

**对账匹配规则**：双方通过「商户交易编号」匹配。微信和支付宝在发起支付时均生成唯一的商户交易编号，AISE 侧保存该编号即可完成逐笔对账。

**对账单导入字段**（尽量与微信/支付宝官方流水字段保持一致）：

| 字段 | 说明 |
|------|------|
| 商户交易编号 | 支付发起时生成的唯一编号，双方通过此字段匹配 |
| 交易金额 | 实际支付金额 |
| 交易状态 | 支付成功 / 已退款 / 已关闭等 |
| 报名信息 | 关联的考试场次、等级、科目 |
| 用户信息 | 关联的学员/家长信息 |
| 支付渠道 | 微信 / 支付宝 / 后台直接开通 |

> 对账完成后，基于以上数据做二次统计：按渠道、按考试场次、按时间段等维度汇总。

### 3.7 订单系统架构

当前 AISE 的订单系统约等于报名管理，每条报名记录携带订单金额和支付状态。讨论结论：

| 编号 | 模块 | 描述 |
|------|------|------|
| R-OS-01 | 通用订单系统 | 从报名管理中拆出独立的订单系统，不与报名强耦合，未来可支持报名以外的支付场景 |
| R-OS-02 | 报名关联 | 订单与报名解耦，通过关联字段绑定（而非订单表直接内嵌在报名表里） |

### 3.8 交易状态 & 流转

#### 3.8.1 状态定义

| 状态 | 含义 | 触发 |
|------|------|------|
| 待支付 | 订单已创建，用户尚未完成支付 | 用户提交报名、发起支付但未完成 |
| 支付成功 | 用户已完成支付 | 微信/支付宝回调确认支付成功 |
| 已关闭 | 订单超时未支付或用户主动取消（未付款） | 支付超时 / 用户取消订单 |
| 退款申请中 | 用户已提交退费申请，等待后台审核 | 仅在阶段 2（报名截止~考前）触发 |
| 已退款 | 退款已执行，费用已原路退回 | 阶段 1 自动退 / 阶段 2 审核通过 |
| 退款驳回 | 后台管理员驳回退费申请 | 仅在阶段 2（报名截止~考前）触发 |

#### 3.8.2 状态流转图

```
                              ┌──────────┐
                              │  待支付   │
                              └────┬─────┘
                        支付成功 │         │ 超时/取消
                        ┌───────┘         └──────────┐
                        ▼                            ▼
                  ┌──────────┐                  ┌──────────┐
                  │ 支付成功  │                  │  已关闭   │
                  └────┬─────┘                  └──────────┘
                       │
          ┌────────────┼────────────┐
          │ 阶段1       │ 阶段2       │ 阶段3
          │ 公开报名     │ 报名截止~考前│ 考试开始~结束
          │             │            │
          ▼             ▼            ▼
   用户点退费       用户点退费      不支持退费
   无需审核         需要审核       （前端无按钮）
          │             │
          ▼             ▼
    ┌──────────┐  ┌──────────────┐
    │  已退款   │  │  退款申请中    │
    └──────────┘  └───┬──────┬───┘
                      │      │
              管理员通过│      │ 管理员驳回
                      ▼      ▼
              ┌──────────┐ ┌──────────┐
              │  已退款   │ │ 退款驳回  │
              └──────────┘ └──────────┘
```

#### 3.8.3 退款联动操作

退款成功后（进入「已退款」状态），可联动触发以下操作：

| 联动操作 | 说明 |
|----------|------|
| 撤销考试资格 | 将该学员从对应考试场次中移除 |
| 撤销证书 | 若已签发证书，撤销电子证书使其失效 |

> 联动操作在后台退费审核时提供勾选项，管理员根据实际情况选择。阶段 1 自动退款同样执行联动。

#### 3.8.4 三个阶段退费规则对照

| | 阶段 1 · 公开报名 | 阶段 2 · 报名截止~考前 | 阶段 3 · 考试开始~结束 |
|------|:--:|:--:|:--:|
| 用户可见退费按钮 | ✅ | ✅ | ❌ |
| 需要后台审核 | ❌ | ✅ | — |
| 退费申请状态 | 直接已退款 | 退款申请中 → 已退款 / 退款驳回 | — |
| 费用原路退回 | ✅ | ✅ | — |
| 联动撤销资格/证书 | ✅ 自动执行 | ✅ 审核时勾选 | — |
| 特殊情况 | — | — | 人工处理 |

## 五、后台页面设计

### 5.1 对账管理（一级菜单）

在 AISE 管理后台新增一级分类「对账管理」，下设两个页面。

#### 5.1.1 交易流水

**定位**：所有交易记录的大表，是整个对账管理的数据底座。微信/支付宝流水导入后与本表比对，差异在此展示。

**页面结构**：筛选区 + 表格 + 导出按钮

**表格字段**：

| 字段     | 来源                | 说明                          |
| ------ | ----------------- | --------------------------- |
| 商户交易编号 | AISE 订单生成         | 支付发起时生成，对账匹配键               |
| 交易金额   | AISE 订单 / 微信支付宝流水 | 实际支付金额（元）                   |
| 交易状态   | AISE 订单           | 待支付 / 支付成功 / 已退款 / 已关闭 等    |
| 支付方式   | AISE 订单           | 微信支付 / 支付宝 / 后台直接开通         |
| 订单类型   | AISE 订单           | 报名 / 其他（后续扩展）               |
| 测评名称   | 关联报名记录            | 对应的考试/测评名称                  |
| 测评 ID  | 关联报名记录            | 对应的考试/测评 ID                 |
| 渠道来源   | 关联报名记录            | 报名的渠道来源（自营 / API 渠道 / 后台开通） |
| 用户名    | 关联用户表             | 下单用户                        |
| 用户 ID  | 关联用户表             | 下单用户 ID                     |
| 交易时间   | AISE 订单           | 支付完成时间                      |

> ⚠️ 表格不展示「对账状态」列。页面只展示原始交易数据，对账匹配由人工线下完成。

**筛选条件**：

- 时间范围（交易时间）
- 支付方式（微信 / 支付宝 / 后台直接开通）
- 交易状态（待支付 / 支付成功 / 已退款 / 已关闭）
- 订单类型（报名 / 其他）
- 测评名称 / 测评 ID
- 用户名 / 用户 ID
- 渠道来源

> ⚠️ 不做行内编辑、不标记。差异处理走工单或线下流程。

**导出**：支持按筛选结果导出 Excel。

#### 5.1.1.1 与报名管理的边界

| 维度 | 报名管理（现有） | 交易流水（新增） |
|------|----------------|-----------------|
| 数据范围 | 所有报名产生的支付数据 | **所有支付场景**的汇总（报名 + 未来其他订单类型） |
| 定位 | 报名业务流程（审核、状态管理） | 资金数据底座（统一查询 + 导出供对账） |
| 操作 | 审核、管理报名状态 | **纯查看 + 导出，不允许编辑/标记** |
| 扩展性 | 与报名强耦合 | 独立订单系统，与报名通过关联字段解耦 |

> 交易流水是汇总所有支付数据的通用订单视图，不局限于报名。当前数据主要来自报名，但架构上预留其他支付场景（如会员、增值服务等）的扩展能力。

---

#### 5.1.2 交易数据统计

**定位**：基于交易流水数据的聚合统计看板，回答「这段时间收了多少、多少人报了、各个渠道分别怎样」等问题。

**页面结构**：时间筛选 + 概览卡片 + 图表区 + 明细表

**1. 概览卡片**（顶部一行）：

| 卡片        | 指标                           |
| --------- | ---------------------------- |
| 总交易金额     | 筛选时间内，支付成功 + 已退款的金额合计（含退款标记） |
| 实收金额      | 筛选时间内，支付成功 - 已退款金额           |
| 总报名人次     | 筛选时间内，所有渠道的报名人次（含已退款）        |
| 有效报名人次    | 筛选时间内，剔除已退款的报名人次             |
| 退款笔数 / 金额 | 筛选时间内的退款总笔数和退款总金额            |

**2. 图表区**：

| 图表 | 类型 | 说明 |
|------|------|------|
| 报名趋势 | 折线图 | 按日/周/月统计报名人次和交易金额趋势 |
| 渠道报名分布 | 饼图 / 柱状图 | 按渠道（微信 / 支付宝 / 后台直接开通 / API）统计报名人次及金额占比 |
| 支付方式分布 | 饼图 | 微信 vs 支付宝 vs 后台直接开通 的交易金额占比 |
| 退款趋势 | 折线图 | 按日/周/月统计退款笔数趋势 |

**3. 维度明细表**（可切换）：

| 维度 | 表格字段 |
|------|----------|
| 按渠道 | 渠道名称、报名人次、支付成功金额、退款人次、退款金额、实收金额 |
| 按测评 | 测评名称、报名人次、支付成功金额、退款人次、退款金额、实收金额 |
| 按日期 | 日期、报名人次、支付成功金额、退款人次、退款金额、实收金额 |

**4. 对账概览**：

| 指标 | 说明 |
|------|------|
| 已对账笔数 | 已完成对账匹配的笔数 |
| 差异笔数 | 对账有差异的笔数 |
| 差异金额 | 对账差异的金额合计 |
| 未对账笔数 | 尚未执行对账的笔数 |

**交互**：

- 时间范围筛选（默认本月）
- 图表支持点击下钻至交易流水列表
- 支持导出各维度明细表

### A.7 后台页面设计讨论（2026-05-25）

> 我考虑这样设计，在aise后台加一个一级分类「对账管理」，下面有两个页面，一个是「交易流水」，一个是「交易数据统计」。交易流水就是个大表，至少包含这些字段：商户交易编号、交易金额、交易状态、支付方式、订单类型（目前只有一种订单就是报名）、订单信息（测评名称、测评id、渠道来源）、用户名、用户id。交易流水支持筛选查询，支持导出。第二个是交易数据统计，按照聊天记录看看怎么设计这个页面。
