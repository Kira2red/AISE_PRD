# 审查报告 — 证书重新生成方案概要

> 审查对象：`方案概要.md` + `场景锚点.md`
> 参考基线：`20260512 证书签发流程 prd.md`（§2.3 签发链路、§3.1.3 模板生命周期、§3.3 实例管理、§3.5 签发中心、§3.7.3 设计原则）
> 审查日期：2026-08-16

## 发现项列表

### 1.【严重】重新生成期间状态回退「签发中」会外溢到学生端/用户端，方案自相矛盾

- **问题**：方案概要「状态变化」写明重新生成期间证书状态变为「签发中」，同时「不改动的地方」声称 16_学生证书管理、user 端 19/20 页「状态标签自动反映最新状态」——两者叠加意味着：原本显示「已签发」的用户证书，会在学生证书管理页和用户端变成「签发中」。这与同一方案里「旧 PDF 仍可访问」的决策直接矛盾（PDF 能打开，状态却是"签发中"），且用户会误以为证书失效，极易引发客诉。
- **建议**：对外可见状态在重新生成期间保持「已签发」（旧 PDF 继续可访问），新 PDF 替换成功后才更新；「签发中」仅作为内部任务状态在 admin 端可见（如 28 页行内提示"更新中"）。此点需用户拍板，且是验收标准必须覆盖的场景。

### 2.【严重】与签发中心全局启停开关的具体交互未定义

- **问题**：方案概要只说「重新生成任务受签发中心全局启停开关控制」，验收标准第 6 条也只是复述机制，不是可验证的行为。原 PRD §3.5.6 规定开关关闭时「待签发任务暂停入队，新申请直接标记为『签发暂停』」——重新生成任务提交时若开关关闭：按钮是否可点？任务是否悬挂？悬挂多久？若悬挂，已签发的证书将长期卡在「签发中」回退状态（叠加发现 1 更严重）。
- **建议**：明确三种行为之一并写入方案：a) 按钮置灰并提示「签发已暂停」；b) 可提交但任务排队，恢复后自动执行；c) 提交时即校验并拒绝。同时在确认弹窗中预告当前开关状态。需用户拍板。

### 3.【重要】按钮显示条件遗漏「未绑定模板」和「已禁用」实例

- **问题**：方案概要规定按钮仅对「已签发数 > 0 或存在失败记录」的实例显示。但原 PRD §3.3.1 明确 28 页实例存在「未绑定模板」状态，未绑定模板的实例若存在历史证书，点重新生成必然失败。
- **建议**：按钮条件补充「已绑定模板」；同时明确「已禁用」实例是否可重新生成（建议可——禁用语义是"不再生成新证书"，与原 PRD §3.3.3 的 confirm 文案一致）。

### 4.【重要】绑定模板被禁用后重新生成的行为未覆盖

- **问题**：原 PRD §3.3.4 规定「已绑定的模板后续被禁用，实例仍可正常使用但编辑时弹出警告」。本需求「按当前绑定模板重新生成」未说明：模板处于禁用态时点重新生成，是否弹警告？26 页的引导文案对禁用态模板是否也展示？
- **建议**：重新生成确认弹窗在绑定模板为禁用态时追加警告文案；明确禁用模板不影响重新生成（与原 PRD「禁用模板仍可正常签发」口径一致）。

### 5.【重要】重新生成期间模板又被修改——无版本快照定义

- **问题**：方案概要「按当前绑定模板重新渲染 PDF」未定义时点。批量任务异步执行，若任务执行期间运营再次编辑模板，同一批次证书可能渲染出两种样式；且后续无法追溯某张证书当时用的模板版本。
- **建议**：明确「任务提交时对模板做快照，整批证书使用同一快照版本渲染」；可选增强：任务进行中在 26 页提示「有 N 个实例正在使用该模板重新生成」。

### 6.【重要】重跑范围漏了「签发中」状态的证书

- **问题**：方案概要排除了「待签发」（合理），但没有排除提交时处于「签发中」的证书。若把签发中的证书也纳入重跑，会与其原有签发任务并发，产生双签章、双流水号。
- **建议**：明确重跑范围 = 提交时点状态为「已签发」或「签发失败」的记录，排除「待签发」与「签发中」；此规则写入确认弹窗文案。

### 7.【重要】任务结果反馈缺失，部分失败后无「只重跑失败」路径

- **问题**：方案概要只有「按钮置灰防重复」，任务完成后运营无任何结果反馈（成功几张、失败几张、失败原因）；部分失败后按钮恢复可用，运营再点一次会对已成功的证书重复签章——第三方签章 API 通常按次计费，浪费额度。防重复还存在提交窗口：确认后到任务记录落库之间有延迟，连点可能提交两次。
- **建议**：a) 确认后前端立即置灰（乐观禁用）；b) 实例行增加「上次重新生成结果」提示（成功 N / 失败 M / 失败原因入口）；c) 评估提供「仅重跑上次失败」入口或至少说明二次重跑的影响。

### 8.【重要】验收标准未覆盖异常分支

- **问题**：6 条验收标准全部是主流程，未覆盖：重生成失败后旧 PDF 保留与状态回滚、模板禁用态重生成、部分成功/失败的结果展示、未绑定模板时按钮不显示、重新生成期间用户端状态呈现（发现 1）、重跑范围排除签发中（发现 6）。
- **建议**：按发现 1–7 逐条补充验收条款，至少补齐「失败兜底」与「状态呈现」两条。

### 9.【重要】重新签章后验签地址/业务流水号与证书编号的一致性未定义

- **问题**：原 PRD §2.3 签发成功保存「证书编号、PDF 地址、验签地址」，签章 API 提交「业务流水号」。方案概要只保证「证书编号不变」，但重新签章必然产生新的验签地址和流水号——编号不变但验签体系能否通过编号查到最新 PDF？旧验签地址失效后的对客口径是什么？均未提及。
- **建议**：明确重新生成后的验签地址更新规则（编号不变、验签地址指向新 PDF）；若签章 API 按次计费，在确认弹窗中展示本次签章总量与成本提示。

### 10.【重要】「签发日期保留原日期」与签章平台时间戳的口径歧义

- **问题**：拍板结论「签发日期保留原日期」只定义了渲染字段，第三方电子签章平台通常记录签章时间戳为重新生成时刻。证书上日期与验签平台时间不一致的对外口径未明确，验收时易起争议。
- **建议**：明确「证书上『签发日期』字段保留原值；签章平台记录的签章时间为重新生成时间，两者不做对齐」，或给出用户期望的另一种口径。

### 11.【建议】与签发中心既有「重签/批量重签失败」能力的边界与并发冲突未说明

- **问题**：签发中心已有单条重签（已签发/失败）和批量重签失败。新入口在 admin 端做「已签发+失败一起重跑」，两边可能同时对同一实例/证书发起重签。原 PRD §3.7.3 设计原则「电子签发的详细状态管理在签发中心」「admin 运营后台不关心签发内部流水线」被本方案部分打破，未说明原则是否修订。
- **建议**：明确同一证书同时只允许一个重签任务（互斥校验）；在 PRD 中说明设计原则的更新——admin 端现在可感知「签发中」与发起批量重跑，签发中心仍保留单条/批量失败重签。

### 12.【建议】确认弹窗缺少总量与影响提示

- **问题**：弹窗只显示已签发数、失败数，未显示合计总量。大型测评可能上千张证书，运营对任务规模与签章成本没有感知，红色警示按钮不足以支撑决策。
- **建议**：弹窗增加「本次将重新签章共 N 张」及耗时/成本提示（若 API 计费）。

### 13.【建议】26 页「使用实例数」统计口径未定义

- **问题**：改动 2「显示该模板已被多少个证书实例使用」未说明是否包含已禁用实例。已禁用实例同样可能需要重新生成，口径不一致会导致运营误判。
- **建议**：明确口径 = 所有绑定该模板的实例（含已禁用），引导文案与数字口径保持一致。

### 14.【建议】重新生成结果是否接入 19_消息中心未提及

- **问题**：原 PRD 改造过 19_消息中心，「不改动的地方」未列消息中心。批量任务完成/失败是否推送消息没有结论。
- **建议**：明确本期是否接入消息中心（不接则声明「结果仅在 28 页查看」，避免研发自行发挥）。

## 总体结论

方案方向与已拍板决策一致、改动范围克制（仅 28/26 两页），但「重新生成期间的状态呈现」与「和现有签发管道/签发中心的边界」两大块定义不足——其中状态外溢用户端（发现 1）和全局开关交互（发现 2）会直接影响用户信任与任务悬挂风险，属于必须补齐后才能进入 Demo/PRD 阶段的阻塞项；其余发现建议在方案概要修订时一并吸收。
