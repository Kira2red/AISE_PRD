### 2. 方案正文

#### 2.1 背景与目标

**目标产品/平台**：AISE 考试系统，覆盖三条入口——爱测评答题端（设备检测/检录/答题）、AISE 用户端（我的活动/我的考试）、iceping 端（答题入口）。本子任务 S1 聚焦「手机端检录」在手机监考通道内的触发与配置逻辑，不涉及电脑端检录页改造。

**核心用户画像**：无电脑摄像头的考生（典型为台式机未配外接摄像头）。该类考生电脑端设备调试无法通过，需走「手机监考」备选通道（依据：手机监考 PRD §1.2 业务诉求，D 级运营反馈，无量化数据）。

**现状与问题**：
- 手机监考通道现有流程为「扫码 → 引导页 → 直播页」（手机监考 PRD §2），**全程无检录环节**。
- 电脑端检录依赖电脑摄像头拍照（检录 demo `10_检录.html`：左视频实时画面 + 拍照 + 检录视频）。无摄像头考生在电脑端同样无法完成检录。
- 检录是考试级配置（强制/非强制/不开启三态）且侧边栏常驻「检录状态徽章」（依据：平台能力梳理《AISE&爱测评平台能力梳理.md》§考试保障）。手机监考通道若缺检录，将造成「检录配置强制但手机通道无检录记录」的覆盖缺口。

**目标**：在手机监考通道的「扫码 → 引导页」之间插入「手机检录页」，使走手机监考的考生能在手机上完成检录（拍照 + 检录视频），保证检录三态配置在所有进入考试的通道上一致生效。检录配置沿用线上三态，token/URL 沿用手机监考既有机制。检录拍照采用前置摄像头自拍考生正面照（锁定决策 8）。

#### 2.2 用户故事与用户旅程

| 用户故事 | 用户价值依据等级 | 来源 |
|---------|----------------|------|
| US1 作为无电脑摄像头的考生，我希望扫码手机监考时也能在手机上完成检录，这样不会因无法检录而被卡在考试入口之外 | D 级（运营反馈，无量化数据） | 手机监考 PRD §1.2「部分考生电脑无摄像头，导致设备调试无法通过、无法进入考试」 |
| US2 作为已用电脑完成过检录、又额外扫码手机监考的考生，在**非强制档**我可以跳过手机检录直接进入引导页（不被迫二次复杂检录）；在**强制档**即使已电脑检录，扫码手机监考仍须再次完成手机检录（锁定决策 4「不去重」的既定代价，非本故事的价值主张） | E 级（经验判断，锁定决策 4 的直接后果，仅辅助） | 锁定决策 3「三态沿用」+ 锁定决策 4「双重检录不去重」 |
| US3 作为考试运营/监考方，我希望检录三态配置在手机监考通道同样生效，所有进入考试的考生都有可追溯的检录记录 | D 级（线上既有机制一致性） | 平台能力梳理「检录页按考试配置强制/非强制/不开启」；候考 PRD §3.3「检录沿用现有三档」 |

> US2 修订说明：原表述「希望手机端不强制我再做一次复杂检录（非强制档可跳过）」在强制档「无跳过 + 不去重」下不成立。现改写为如实描述——「不被迫二次检录」期望**仅在非强制档成立**，强制档须再次检录（锁定决策 4 的既定代价），并维持 E 级标注。

**核心用户旅程（无摄像头考生，检录=强制档）**：

```
电脑端设备调试页 → 电脑摄像头检测失败 → 扫码手机监考
  → 手机打开 /proctor/mobile?token=…（落地即被服务端分流）
  → 手机检录页（前置摄像头自拍 → 检录视频 → 完成）
  → 引导页（摆放指引 → 「开始监考」）
  → 直播页（切后置摄像头推流）
  → 电脑端感知手机连接 → 摄像头项标记通过 → 进入考试
```

**关键旅程差异**：与电脑端检录旅程（检录完成 → 候考等候页/直接进考试，候考 PRD §3.3）不同，手机端检录完成/跳过后的去向是**引导页**，手机监考通道完全不经过候考流程（锁定决策 6）。检录页摄像头为**前置**（自拍正面照），直播页切**后置**（拍环境），两页摄像头方向不同（锁定决策 8）。

**F2 修订说明（摄像头方向 + 拍照来源）**：
- 检录页**强制前置摄像头**（`facingMode:'user'`），自拍考生正面照；**不提供翻转切后置**（检录阶段不存在「拍环境」诉求，防止考生误拍环境当作本人）。
- 检录照片**仅实时拍摄**，**禁用相册选图、禁用美颜/滤镜**（对齐电脑端检录 demo `10_检录.html` 的实时画面拍照交互），保证监考端核验的实时性与真实性。
- 进入直播页后按手机监考 PRD §3.3.2 切换/默认后置（`facingMode:'environment'`），继续提供翻转按钮（直播页原有交互不变）。

**F6 修订说明（视频上传时点 + 半完成态）**：
- 照片：点「拍照」即上传（锁定决策 7）。
- 视频：**录制完成即上传**（与「产生即上传」原则一致，避免「已录未传」悬置态）。
- 上传均以 token 反查「考生 + 场次 + 来源通道」落库；照片与视频各自独立上传，可分别成功/失败。

**F8 修订说明（来源通道）**：
- 检录结果存储**新增「来源通道」字段**（手机/电脑），用于：①监考端「查看检录」区分来源通道展示；②「双重检录重复率」指标口径（判断「手机检录前已存在电脑检录记录」需按通道比对）。

**硬件依赖验证小结**：手机检录页唯一硬件依赖为「考生自备手机的前置摄像头」，该硬件为手机监考通道的既有前置条件（直播页已依赖 `getUserMedia`，手机监考 PRD §3.3.2），不存在新增硬件门槛。手机检录照片/视频的分辨率、时长等规格沿用线上检录实现，**线上规格尚未在本方案材料中给出，列入待确认 #2**；前置摄像头分辨率能否满足检录照片规格，同列入待确认 #2。

#### 2.4 核心流程（关键路径描述）

**（1）扫码落地分流（触发条件的工程实现）**

二维码内容沿用现有机制（手机监考 PRD §3.1.2）：`{AISE域名}/proctor/mobile?token={token}`，token 由服务端在考生进入设备调试页时生成，关联「考生 ID + 考试场次」。**扫码落地时由服务端读该场次的检录配置做分流**：

| 检录配置 | 落地行为 |
|---------|---------|
| 强制 / 非强制 | 重定向至 `/proctor/mobile/checkin?token={token}`（手机检录页） |
| 不开启 | 重定向至 `/proctor/mobile/guide?token={token}`（引导页，原流程，无检录页） |

> 触发条件 = 「云端开检录功能（强制或非强制）」 **且** 「考生走手机监考通道（扫码）」。两条件为 AND 关系；不开启档即「未开检录」，直接走原流程。

**（2）三态分支（手机检录页内行为）**

| 检录配置 | 检录页行为 | 完成/跳过后去向 |
|---------|-----------|----------------|
| 强制 | 必须完成拍照 + 检录视频方可进入引导页，**无「跳过」按钮** | 完成 → 引导页 |
| 非强制 | 有「跳过」按钮，可跳过检录直接进入引导页 | 完成或跳过 → 引导页 |
| 不开启 | 不出现检录页（分流直接到引导页） | — |

> 强制档的阻塞语义：未完成检录不能进入引导页/直播页，即不能开始推流。此「检录阻塞推流」的产品取舍见 §2.7 风险 R3。
> 检录页摄像头方向：**前置**（`facingMode:'user'`，锁定决策 8）；直播页**后置**（`facingMode:'environment'`，沿用手机监考 PRD §3.3.2）。

**（3）token 衔接（三页同 token 透传）**

```
扫码入口   /proctor/mobile?token={token}          （落地分流，不渲染页）
手机检录页 /proctor/mobile/checkin?token={token}  （新增）
引导页     /proctor/mobile/guide?token={token}    （现有）
直播页     /proctor/mobile/live?token={token}     （现有）
```

- token 复用现有生成与绑定机制（手机监考 PRD §3.1.2/§3.4）：同一考生同一场次复用同一 token，不因新增检录页而重新生成。
- 三页间跳转通过 URL query 透传同一 token，检录页不重新发 token。
- 检录结果上传时以 token 反查「考生 ID + 考试场次」落库，与推流会话同源。

**token 泄露面安全说明（回应 #7）**：
- 新增检录页后，token 经 URL 三页透传，其泄露后果由原先的「劫持推流（冒充本人视频）」扩大到「**代考生伪造检录记录**」——持有 token 者可上传照片/视频冒名完成检录，使「代考」的检录环节也可被伪造。
- 定性：token 泄露本身已是最高严重级风险（可直接劫持推流冒充本人），伪造检录是其在检录页上的**次级衍生后果**，不构成新的独立高危面，但需在方案中明示。
- 缓解沿用既有机制（手机监考 PRD §3.4）：token 绑定「考生 + 场次」、短有效期（考试窗口 + 30 分钟缓冲）、单路踢旧（同一考生仅 1 路）、HTTPS 传输。
- 新增缓解：检录照片**仅实时拍摄、禁用相册/滤镜**（F2），抬升伪造门槛（伪造者须实际拍摄到目标考生，而非仅凭 token 上传任意图）。
- 残余风险与「劫持推流」同级，纳入既有 token 安全治理，S1 不单独新增大额安全建设。

**（4）检录完成/跳过的去向（候考边界）**

- 手机检录完成/跳过 → **引导页**（非候考页、非等候页）。
- 手机监考通道**完全不经过候考流程**（不等候、不倒计时、无「开始考试」按钮）——与候考 PRD §3.3 电脑端检录出口（候考窗口内 → 等候页）形成明确分界。
- 候考时序（开考前 N 分钟入口三态、等候页倒计时）只作用于电脑端入口，手机端不参与候考时序判定。

**（5）电脑端检录结果消费（S1 边界内的推断，待确认 #1）**

手机检录结果上传落库（绑定账号 + 场次 + 来源通道）后，电脑端设备调试页点击「进入测评」时，服务端按「账号 + 场次」查询检录状态：**已存在检录记录（含手机端完成）→ 不重复电脑检录**，直接进入下一环节（候考/考试）。此推断与候考 PRD §3.4「检录结果与账号绑定，已完成检录不重复」一致。

#### 2.5 边界与异常场景（穷举）

**A. 双重检录边界（锁定决策 4 的精确语义，立论已修正）**

| 场景 | 行为 |
|------|------|
| 考生电脑有摄像头、已电脑检录通过，又扫码手机监考 | 手机扫码**仍进检录页**（不去重），允许再次检录；重复检录结果以最后一次为准（覆盖） |
| 考生电脑有摄像头、尚未检录，先扫码手机监考完成手机检录 | 电脑端后续「进入测评」识别已有检录记录，不重复电脑检录（推断，待确认 #1） |
| 考生同 token 反复进入手机检录页（刷新/重进） | 可重复拍照，检录结果覆盖（以最后一次为准）；不做「已完成即跳过」拦截 |

> 「不去重」的精确语义（回应 #3 修正）：
> - **手机检录页入口不做任何前置状态查询**（不查电脑摄像头状态、不查电脑检录是否完成）——这是锁定决策 4 的最小改动语义。
> - 立论修正：原「避免跨端状态同步」不成立——跨端同步**本就存在**（电脑端「进入测评」按账号+场次去重，需查询手机检录记录，候考 PRD §3.4）。「不去重」的真实收益是「手机入口零查询、流程最短、无前置阻塞」。
> - **跨端不对称（预期行为，非缺陷）**：手机入口不去重 + 电脑端去重叠加，客观产生——「电脑→手机」方向（先电脑检录再扫码手机）产生**两份**记录；「手机→电脑」方向（先手机检录再电脑进入）只产生**一份**记录。本方案如实标注为**预期行为**，其代价由 §2.6「双重检录重复率」指标量化，无需额外对称化改造。

**B. token 相关边界**

| 场景 | 行为 |
|------|------|
| token 过期（考试窗口 + 30 分钟缓冲之外） | 沿用现有机制，扫码落地即失效，检录页/引导页/直播页均无法进入（手机监考 PRD §3.4） |
| token 被新连接踢旧（同一考生仅 1 路手机流） | 沿用现有机制，旧会话失效（手机监考 PRD §3.4） |
| 三页间 token 丢失/被篡改 | 引导页/直播页校验 token 无效 → 阻断进入，引导回扫码 |

**C. 检录配置与考试状态组合**

| 场景 | 行为 |
|------|------|
| 检录=强制，考试已开考后才扫码 | 仍进检录页，须完整完成拍照 + 检录视频才可进引导页/直播页（强制档无跳过、**无时间豁免、不兜底**） |
| 检录=不开启，考试任意时刻扫码 | 原流程（扫码 → 引导页 → 直播页） |
| 检录=强制，手机摄像头权限被拒 | 检录页显示摄像头不可用 + 重试；无法完成检录则被卡在检录页（见风险 R3） |

> 开考后强制档仍须完整检录的取舍说明（回应 #2）：
> - 候考 PRD 的「开考后一键进入、不占用考试时间」收益，靠**提前候考**实现（开考前完成检测检录，开考后一键进入），而非靠「开考后豁免检录」——开考后进场在电脑端同样要检录（候考 PRD §2.1：开考后入口「开始考试」→ 设备检测 → 检录 → 直接进入考试）。
> - 若手机端开考后豁免，则无摄像头考生可故意开考后扫码绕过强制检录，与电脑端开考后强制检录不对称，破坏强制档语义（US3：所有进入考试的考生都有检录记录）。
> - 故默认「**不豁免、不兜底**」；是否需「仅拍照免视频」或「时间豁免」作为强制档的例外，属产品决策，保留为待确认 #4。

**D. 候考边界场景**

| 场景 | 行为 |
|------|------|
| 考试配置了候考，考生走手机监考 | 手机端无等候页/倒计时；候考时序由电脑端入口承载，手机端不受影响 |
| 考试未配置候考，考生走手机监考 | 手机端仍无候考（本通道本就无候考），无差异 |
| 模拟测 + 手机监考 | 检录完成/跳过 → 引导页 → 直播页（手机端同正式测去向，不经候考、不经模拟测入口） |

**E. 拍照即上传 + 视频上传边界（含半完成态，回应 #5）**

| 场景 | 行为 |
|------|------|
| 拍照后上传失败（弱网/断网） | 检录页提示重试，未成功上传前不可进入引导页（强制档）；非强制档可跳过 |
| 录制完成、视频上传失败 | 检录页提示重试上传；未成功上传前不可进入引导页（强制档）；非强制档可跳过 |
| 拍照上传成功、退出检录页（照片已传、视频未录/未传） | 重进检录页时识别「仅照片」的部分记录，**续接**：展示已拍照片 + 提示「继续录制检录视频」；也可重新拍照覆盖重做 |
| 拍照后、上传前考生退出检录页 | 本次拍照未落库，重进需重新拍照（「产生即上传」下不存在「已拍未传」的悬置状态） |
| 照片 + 视频均已上传完成，考生重进 | 按「不去重」允许重新检录覆盖（以最后一次为准），不拦截 |
| 检录视频录制中切后台/锁屏 | 视频录制中断，需重新录制（沿用线上检录视频规则，规格待确认 #2） |

> 半完成态语义：检录结果按「账号 + 场次 + 来源通道」存在「无记录 / 仅照片 / 完整（照片+视频）」三态，**仅「完整」视为检录通过**；「仅照片」为部分完成，不计入检录通过，重进续接补齐视频。此需服务端支持部分记录查询，见待确认 #6。

#### 2.6 成功度量与指标

| 指标 | 定义 | 数据来源 / 估算依据 |
|------|------|-------------------|
| 手机检录完成率（强制档） | 检录=强制 + 手机监考的场次中，完成手机检录（完整）的扫码会话占比 | 待验证（需埋点：扫码会话数 + 检录成功数，二者以 token 关联） |
| 手机检录完成率（非强制档） | 检录=非强制 + 手机监考场次中，完成检录（未跳过）的扫码会话占比 | 待验证（埋点同上，拆分「完成/跳过」） |
| 检录覆盖缺口 | 检录=强制 + 手机监考场次中，「无任何检录记录」的考生占比（目标 0） | 待验证（爱测评后台检录记录 vs 手机监考考生清单比对） |
| 双重检录重复率 | 手机检录前已存在「来源通道=电脑」检录记录的会话占比（评估「不去重」代价，依赖来源通道字段） | 待验证（检录记录按账号+场次+来源通道比对） |
| 手机检录耗时 | 进入检录页 → 检录完成（或跳过）的中位时长 | 待验证（需埋点；用于评估检录页对开考入场节奏的影响） |

**埋点（S1 建议，参照候考 PRD §5 风格）**：`手机检录_扫码落地`、`手机检录_进入检录页`、`手机检录_拍照上传成功/失败`、`手机检录_视频上传成功/失败`、`手机检录_完成`、`手机检录_跳过`、`手机检录_半完成态续接`、`手机检录_去向引导页`。

> 所有指标均为「待验证」，首次上线以埋点数据回填基准值；不预置假设数值，避免凭空编造。「双重检录重复率」口径依赖 §2.3 F8「来源通道」字段。

#### 2.7 风险与依赖

| # | 风险/依赖 | 等级 | 说明 | 验证状态 |
|---|----------|------|------|---------|
| R1 | token 生成/绑定机制沿用，若现有「同一考生同一场次复用 token」逻辑有异常，检录结果将无法正确落库到对应考生 | 🟡 一般 | 检录结果依赖 token 反查考生+场次 | 依赖手机监考 PRD §3.4 既有实现，未单独验证 |
| R2 | 扫码落地分流依赖服务端读取「检录配置」，需确认检录三态配置在考试管理中可被 `/proctor/mobile` 落地接口实时读取 | 🟡 一般 | 配置读取延迟/缓存可能导致分流错误 | 待确认 #3 |
| R3 | 强制档「检录阻塞推流」：无摄像头考生若手机摄像头亦不可用，会被卡在检录页，无法进入推流，形成新阻塞点；开考后扫码同样阻塞 | 🟠 严重 | 原手机监考通道无此阻塞；新增检录页引入；开考后无豁免放大该阻塞 | 待确认 #4（是否需强制档的兜底/豁免） |
| R4 | 双重检录不去重可能产生多份检录记录，监考端「查看检录」需明确展示哪一份，并区分来源通道（手机/电脑） | 🟡 一般 | 影响监考端检录查看体验 | 待确认 #5 |
| R5 | 手机检录视频上传的带宽/时长规格未知，可能影响弱网考生完成率 | 🟡 一般 | 依赖线上检录视频规格 | 待确认 #2 |
| R6 | 电脑端「进入测评」如何消费手机检录结果（放行判定）未在既有 PRD 明确 | 🟠 严重 | S1 仅给出推断（§2.4(5)），未锁定 | 待确认 #1 |
| R7 | token 泄露面由「劫持推流」扩大为「代考生伪造检录记录」 | 🟡 一般 | 新增检录页扩大 token 泄露后果（§2.4(3) 已补安全说明）；缓解沿用既有机制 + 仅实时拍摄 | 纳入既有 token 安全治理，未单独新增验证 |
| R8 | 半完成态（照片已传、视频未传）若无续接，考生需重复拍照，体验差 | 🟡 一般 | 依赖服务端支持「仅照片」部分记录查询（§2.5 E） | 待确认 #6 |

**硬件依赖风险（单独列出）**：手机检录页依赖「考生自备手机的前置摄像头」，该硬件为手机监考通道既有前置（直播页 `getUserMedia`），验证状态=已由手机监考 PRD §3.3.2 确认存在依赖，无新增硬件。手机前置摄像头分辨率能否满足检录照片规格，**待确认 #2**。
