## 三、需求变更 + 新需求：报名与信息审核闭环（P4~P9 合并立项）

> P4/P5/P6 三项变更有共同载体（admin 11 报名管理 + 25 用户信息审核），与 P7/P8/P9 新需求互相咬合，**合并为一个需求文件夹**立项：`20260911 报名信息审核闭环`（名称待定）。

### 职责重划分（本需求的核心口径）

| 页面 | 现状 | 新口径 |
|------|------|--------|
| 11 报名管理 | 报名记录 + 订单抽屉；照片审核已迁出（20260514） | 承载报名时**全部**信息：考生信息快照 + 照片 + 准考证图 + 信息状态列；**报名时的信息/照片审核操作在本页完成** |
| 25 用户信息审核 | 身份信息变更 + 照片审核双类型工作台 | 只管**报名后的信息修改申请**审核；照片审核与首次信息审核移入 11 |

### P4 待审期间允许覆盖修改（反转 20260404 口径）

- **现状**：20260404 考中考后修改 PRD §5.3.4 定为「同一账号存在待审记录时，禁止在前台发起新的资料修改申请」；§5.3.3 定为待审期间表单只读、保存按钮禁用。
- **新口径**：待审期间学生**可以**继续在个人中心修改并再次提交；新提交**覆盖上一条申请**，审核始终以最新提交为准。
- **改动点**：
  1. 用户端个人中心（user/13）：待审期间表单保持可编辑，提示文案改为「您有一条信息修改申请审核中，再次提交将覆盖当前申请」。
  2. 覆盖规则：新提交生成时，旧工单状态置为「已作废（被覆盖）」，不再进入待办队列；审核列表默认不显示已作废记录，可筛选查看。
  3. 审核快照：审核通过前，对外（准考证、报名核准、证书）仍展示修改前的原值——沿用 20260404 §5.3.4「考试校验隔离」思路，仅放开「禁止再次发起」这一条。
- **落地方式**：在新需求 PRD「报名后信息修改审核」章节声明对 20260404 §5.3.3/§5.3.4 的修订；20260404 文件夹改动日志登记修订指引。

### P5 信息审核显示新旧对比（PRD 已写、demo/线上未落）

- **现状**：20260404 §5.3.2 已定「左右分栏对比修改前后信息」，但 25 demo 审核详情实际只有照片大图+证件信息平铺，无对比结构（2026-09-11 核实：demo 全文无「修改前/修改后/原值/新值」任何字样）。
- **改动点**：
  1. 25 审核详情视图重构：逐字段对比表（字段名 / 修改前 / 修改后 / 变更标记），仅变更字段高亮，未变更字段折叠或灰显。
  2. 25 列表补列：**申请时间**（已有提交时间则沿用）、**状态**（待审核/已通过/已驳回/已作废）。
  3. demo 25 同步改造（开工时做，本文档阶段不动）。

### P6 照片审核回到报名管理（反转 20260514 迁移方向）

- **现状**：20260514 PRD 把照片审核从 11 迁到 25，理由是统一审核工作台。
- **新口径**（按运营建议）：照片审核回归 11 报名管理，与报名信息一体呈现；25 只保留报名后修改申请审核。
- **改动点**：
  1. 11 报名记录表格/抽屉：增加考生照片缩略图列 + 照片审核状态（待审核/通过/驳回）+ 行内通过/驳回操作。
  2. 25 页面「审核类型」筛选与工单类型调整：移除「照片审核」类型（存量已办结照片工单留档可查）；类型变为「信息修改申请」（+ P7 的「首次报名信息审核」若落在 25，见下）。
  3. 用户端照片审核状态提示位置不变（个人中心状态卡片保留）。
- **落地方式**：20260512 5 月需求文件夹改动日志登记方向反转及原因（考务老师反馈）；细节在新需求 PRD 中定义。

### P7 新注册/首次报名信息人工审核（新增，轻方案）

- **现状**：注册=手机号+验证码即完成（user/01），首次报名填写的考生信息（姓名/证件号/监护人等）**提交即生效，无任何审核环节**；全仓库无注册审核 PRD（2026-09-11 核实）。
- **方案（轻方案）**：
  1. 首次报名提交的考生信息状态=「待审核」，生成审核工单；照片审核同链路（P6 已定在 11）。
  2. 审核入口在 11 报名管理（与 P6 一致，报名时的信息+照片审核都在报名管理完成）。
  3. 审核通过前：考生可正常登录、浏览、支付报名（不阻断转化）；信息状态列显示「待审核」（联动 P8）。
  4. 审核驳回：考生在个人中心修改后重新提交，重新进入待审核（复用 P4 覆盖逻辑）。
  5. 存量已注册用户不回溯，默认视为已通过。
- **边界**：审核对象是首次报名的信息，后续信息修改走 25 既有流程；定制报名（元创S营类）已有自己的审核制，不重复套用。

### P8 报名管理显示信息状态列（新增）

- 11 报名记录增加「信息状态」列：待审核 / 已通过 / 已驳回（定制报名沿用其审核中/已通过/已驳回既有口径）。
- 点击状态可跳转/展开对应审核操作（待审核行直接提供通过/驳回，与 P6/P7 同一交互）。

### P9 报名管理新增准考证图片列（新增，按运营建议=系统生成的准考证）

- 11 报名记录增加「准考证」列：展示该学生本场考试的准考证图片预览（缩略图，点击放大查看）。
- 数据来源：user/18 我的准考证同源（系统按报名记录生成）；未生成（如未支付、信息待审核）显示占位。
- 展示形态（渲染为图片 vs 前端样式还原）属技术实现，PRD 只定义展示效果，实现方式研发评估。

## 四、新提需求：admin 考生答卷查询（P10 单独立项）

> 老师指正：应在 AISE admin 后台看，不在爱测评后台操作。单独立项：`20260911 考生答卷查询`。

- **痛点**：运营在 AISE admin 无法按学生维度找到答卷与答题状态，需登爱测评后台逐场翻。
- **方案**：admin 端新增「考生答卷查询」页（编号顺延 35，挂考试管理分组）：
  1. 查询条件：学生姓名 / 手机号 / 证件号（至少一项，支持模糊），可选限定考试或活动范围、考试状态。
  2. 结果列表（一行=学生×考试）：学生信息、考试名称、答题状态（未进入/进行中/已交卷/缺考）、开始时间、交卷时间、成绩（已发布时）、切屏次数。
  3. 深度操作跳转：查看检录照片/录像/录屏/行为日志/试卷时，携带定位参数跳转 iceping 测评详情对应面板（复用爱测评已有能力，不在 admin 重建监控页——线上实现简单）。
- **数据依赖**：iceping 考生监控与答卷数据（07 测评详情同源）；AISE 侧仅做跨考试聚合查询视图。
