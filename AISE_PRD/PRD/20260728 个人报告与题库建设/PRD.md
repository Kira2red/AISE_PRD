#### 1.4.2 掌握度判定

（出处：业务需求梳理.md 1.4.2）

| 知识点作答掌握率 | 掌握状态 |
|----------------|---------|
| < 60% | 重点提升 |
| ≥ 60% | 稳定掌握 |

- 掌握率公式：**该知识点关联题目的得分之和 ÷ 该知识点关联题目的满分值之和**（业务需求梳理.md 1.4.2）。
- 实现规格（推导自 1.4.2）：
|  - **聚合粒度取二级知识点（推导依据）**：知识树结构为「一级知识模块 → 二级知识点 → 三级标签」，其中三级标签「需入库，前端不展示」（业务需求梳理.md 1.4.1 补充说明 #1）；报告展示粒度为一/二级（业务需求梳理.md 1.1 模块 3「按一级、二级知识标签展示掌握状态」），故取二级为聚合与展示的公共粒度。
|  - 按题目「知识点」字段的**二级**知识点聚合题目；掌握率 = sum(关联题目得分) / sum(关联题目满分值)。
|  - **分母口径**：掌握率分母（满分值之和）仅统计**带「知识点」字段**的题目；题目无「知识点」字段时不进入分子/分母（不拉低掌握率）。该降级处理见 **S4-1-2**（交叉引用）。
|  - 以浮点计算、不做取整/四舍五入（与 1.3.1 总分口径一致），再与 0.6（60%）比较。
|  - 边界含等号：掌握率 = 60%（0.6）时判定为「稳定掌握」。
|  - 若某二级知识点下无关联题目（满分值之和为 0，除数为 0），掌握率未定义；原文未定义该边界，需另行确认（本章不编造规则；处理建议见 **S4-1-3**，交叉引用）。
|  - **UI 展示映射**：「稳定掌握」→ 状态标签展示「稳定」；「重点提升」→ 展示「重点提升」（出处：样式参考.md 5.3 组件样式要点，见 S2.4 M3；标签语义与色值待 Q8/Q9 采样核验，见 S2.6）。

#### 1.4.3 展示排序

（出处：业务需求梳理.md 1.4.3）

| 层级 | 排序规则 |
|------|---------|
| 一级知识模块 | 按知识树顺序展示 |

### 1.5 考级具体表现

#### 1.5.1 两套展示逻辑

（出处：业务需求梳理.md 1.5.1）

| 规则项 | 满分画像（总分 = 100） | 非满分画像（总分 < 100） |
|--------|---------------------|----------------------|
| 触发条件 | 总分等于 100 | 总分小于 100 |
| 展示题目数 | 1 道 | 2 道 |
| 题目选取 | 首道满分的编程题 | 首道错误的客观题 + 首道扣分的编程题 |
| 排序 | / | 按题号展示，客观题先于编程题；如客观题全对，则仅展示编程题 |
| 展示答案 | 只展示学生作答，不展示正确答案 | 展示学生作答与正确答案 |
| 作答点评 | 本题目作答达到要求，完整完成任务。太棒了！ | 建议重点提升【题目二级标签知识点】。 |

实现规格（推导自 1.5.1 + 1.5.3）：
- 触发条件与 1.3.1 共用同一正式总分 score（float 比较）：score == 100 → 满分画像；score < 100 → 非满分画像。
- 名词定义：「满分编程题」= 该题得分 = 该题满分值的编程题；「扣分的编程题」= 该题得分 < 该题满分值的编程题；「错误的客观题」= 该题得分未达满分（含 0 分）的客观题。「首道」按题号升序取题号最小者（排序口径推导自 1.5.1「按题号展示」）。
- 非满分排序：两题均存在时客观题在前、编程题在后；客观题全对（不存在错误客观题）时仅展示编程题（业务需求梳理.md 1.5.1）。
- 非满分点评文案中【】内填充该题目的**二级知识点**名称（1.5.1 + 1.5.3）。
- 边界（原文未定义，需另行确认，本章不编造规则）：① 非满分画像中若不存在「首道扣分的编程题」（编程题全部满分），展示内容未定义；② 满分画像中若不存在「满分的编程题」，展示内容未定义。实现时以上述原文规则为准，并预留降级策略的确认点。

#### 1.5.2 编程题截断规则

（出处：业务需求梳理.md 1.5.2）

| 规则项 | 内容 |
|--------|------|
| 触发条件 | 学生作答代码行数较多时 |

### S3.4 PDF 下载实现方案对比（待技术评审）

> 背景：业务需求梳理.md 仅要求「支持下载为 PDF」，未定实现方式。以下为可选方案对比，**选型待技术评审确认**，本 PRD 不拍板。

| 方案 | 实现方式 | 优点 | 缺点 / 风险 | 建议适用 |
|---|---|---|---|---|
| 方案 A：前端打印 / 截图 | 页面 CSS `@media print` 分页样式 + 浏览器「打印→另存为 PDF」；或前端合成（html2canvas + jsPDF） | 实现成本低；与页面样式天然一致；无需后端资源 | 分页控制弱，长报告易截断；依赖浏览器打印行为，跨浏览器/移动端差异大；移动端体验差 | Web 端快速上线场景 |
| 方案 B：后端生成 PDF | 服务端渲染报告 HTML → Headless 浏览器（Chromium / Puppeteer 等）或 PDF 引擎生成文件，用户端直接下载 | 输出稳定一致、分页可控；Web 与移动端均可直接下载；可与证书 PDF 生成链路复用技术栈（证书 PRD 已具备 PDF 生成能力） | 开发成本较高；需维护报告模板；中文字体嵌入需处理 | 推荐候选（与证书链路一致性更好），仍需技术评审定夺 |

> 结论：两方案均可行，权衡点为开发成本、输出一致性、移动端体验、与证书 PDF 链路的技术栈复用，最终选型**待技术评审确认**。

### S4.0 总则

#### 4.0.1 处理策略四类定义

| 策略 | 定义 | 适用原则 |
|------|------|---------|
| 拦截 | 在数据校验层/触发层阻止异常数据进入生成或展示链路，不产出错误内容 | 能拦截则拦截，优先于一切降级 |
| 降级 | 异常数据无法拦截时，以占位/局部隐藏/通用文案保证报告可读、可渲染，不破坏五模块骨架（S1 1.1 模块顺序固定、不允许省略） | 拦截失败后的第二优先级 |
| 重试 | 生成链路/下载等可恢复性失败，按重试机制自动或人工重新执行 | 仅限可恢复失败，需有次数/超时上限 |
| 提示 | 用户端/管理端的异常提示文案与呈现形态 | 所有异常最终必须有可理解的呈现 |

优先级：**拦截 > 降级 > 重试 > 提示**；同一场景可组合使用（如「拦截 + 提示」「降级 + 提示」）。

#### 4.0.2 用户端呈现总约束

- 报告**用户端可见**状态仅三态：未生成 / 生成中 / 已生成（S3.1.5 状态机；20260806 修订后另含服务端「生成失败」任务态，见 S4-2-1）。**生成链路失败、重试中等服务端任务状态不新增用户端可见状态**：失败考生用户端表现等同「未生成」（不展示「查看报告」按钮）（S3.2.2「成绩未发布或报告生成中的卡片不展示该按钮」）；失败原因与重试操作仅 admin 端可见（建议，见 S4-2-1）。
- 所有「已生成」报告的内容必须来自通过校验的数据；校验不通过即不置「已生成」。
- 异常提示文案统一登记于本章各表「处理策略」列；涉及警示色的样式遵循 S2 配色板（如 C7 高亮粉红系），具体样式归属 S2 实现，本章不重复定义。
- 本章所有「建议」值（重试次数、超时时长、保留期、文案）均为默认建议，最终以需求确认/技术评审结论为准。

### S4.2 生成链路类

> 生成链路以 S3.1 为基线：成绩发布 → 与证书共用触发点 → 按考生批量异步任务入队（消息队列）→ 消费者生成 → 状态置「已生成」→ 展示入口。失败重试与导出文件管理复用 admin 端消息中心（S3.1.4）；重试机制参考证书签发 PRD 2.3「失败重试机制（指数退避 + 次数上限）」（逻辑校验）。

| 编号 | 异常场景 | 触发条件 | 影响 | 处理策略（拦截/降级/重试/提示） | 依据 / 标注 |
|------|---------|---------|------|-------------------------------|------------|
| S4-2-1 | 报告生成任务失败 / 超时 | 消费者生成异常（依赖数据读取失败、渲染异常、服务异常）；任务超时未完成 | 报告状态无法置「已生成」；用户端入口不出现（S3.1.5） | **重试**：失败重试机制，指数退避 + 次数上限（参考证书签发 PRD 2.3，逻辑校验）；**建议**重试上限 3 次（参考导出证书包 PRD「attempt_count < 3」口径，建议值）、单任务超时 30 分钟置失败（参考导出证书包 PRD 超时口径，建议值），避免「生成中」长期悬挂；**记录**：失败记录（含失败原因）回写 admin 消息中心（异步任务/导出文件管理能力，S3.1.4），admin 可查看并手动重试（**建议**）；**用户端**：保持不展示「查看报告」按钮（等同未生成，S3.1.5），**不新增用户端失败态**（S4.0.2）；连续重试失败由 admin 人工介入；**提示**：admin 消息中心展示失败状态与原因 | S3.1.4、S3.1.5；证书 PRD 2.3（逻辑校验）；重试次数/超时值为**建议**（参考导出证书包 PRD 口径） |
| S4-2-2 | 成绩发布与报告生成不同步（批量队列积压） | 大批量考生成绩集中发布 → 队列积压，报告生成滞后于成绩发布 | 成绩已可查但「查看报告」入口迟迟不出现；user/20 出现「有成绩、无报告」中间态 | **拦截（入口约束）**：严格按 S3.1.5 状态机——报告未「已生成」前一律不展示「查看报告」按钮（S3.2.2），不因成绩已发布而提前放行；user/20 按 S3.2.4 按钮并存矩阵执行（报告生成中 → 不展示「查看报告」，证书按钮状态独立）；**提示（建议，需另行确认）**：原文仅规定「不展示按钮」；是否在卡片上增加「报告生成中」灰态占位文案为**建议**增强项，确认前不实现；**容量兜底**：队列限流/削峰见 S4-4-1 | S3.1.5、S3.2.2、S3.2.4；「生成中」占位提示为**建议/需另行确认** |
| S4-2-3 | 报告部分生成（同场考试某考生成功、某考生失败） | 批量任务中个别考生生成失败/超时，其余成功 | 同一场考试部分考生有入口、部分没有 | **隔离**：按考生逐条独立任务（S3.1.4），个别失败不影响其他考生；**不回滚**：不因部分失败回滚已成功报告，已生成报告保持有效；**重试**：失败考生走 S4-2-1 重试/失败记录链路，重试成功后入口自动出现（用户无需操作）；**提示（建议）**：admin 消息中心支持按考试筛选「生成失败」考生并批量重试（复用消息中心能力） | S3.1.3（覆盖所有已批改且有正式总分的考生）、S3.1.4；admin 批量重试为**建议** |
| S4-2-4 | 数据源缺失：未批改完成就触发（触发条件防御） | 成绩发布事件提前/重复到达，批改未完成或正式总分未发布时消费者开始执行 | 报告依赖三类数据（正式总分、题目知识点字段、学生作答，S3.1.2）未齐备 → 产出空/错报告 | **拦截（触发条件）**：触发条件固定为「考试批改完成且正式总分已发布」（S3.1.1），与证书共用触发点（S3.1.2）；**防御实现（建议）**：消费者执行前做数据齐备性校验（正式总分存在、批改状态 = 已完成），不齐备 → 任务不执行、按指数退避延迟重试，**不产出残缺报告、不置失败**（等待数据就绪而非放弃）；**用户端**：未发布/未生成不展示入口（S3.1.5「未生成」态） | S3.1.1、S3.1.2（逻辑校验：三类数据在批改完成、成绩发布后齐备）、S3.1.5；消费者侧防御校验为**建议** |

### S4.3 用户端/体验类

> 用户端基线：入口为 user/15 我的活动、user/20 成绩与证书_独立页（S3.2）；详情页新增，支持 Web/移动端响应式查看与 PDF 下载（S3.3）；渲染验收标准见 S1 1.7 与 S2.5（390×844、正文 ≥15px、辅助标签 ≥12px、核心标题 20–24px）。
