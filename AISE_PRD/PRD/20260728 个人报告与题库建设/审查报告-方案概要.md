# 审查报告 — 「个人考级报告与知识标签管理」方案概要

> 审查结论：**B-（不通过，修订后复审）**

## 🔴 严重问题（必须在 PRD 写作前修正）

### R1. 掌握度阈值与业务需求矛盾（数据规则错误）
- 方案概要 §3.1：「重点提升（<60%）/ 稳定掌握（**≥80%**）」
- 业务需求梳理 §1.4.2：「< 60% 重点提升，**≥ 60% 稳定掌握**」
- 场景锚点 §3.3 同样写成了 ≥80%，方案继承了该错误。
- 这是报告第三章的核心判定规则，写错将直接导致 PRD 和 Demo 全部返工。**以业务需求梳理（运营 PRD 原文）为准：60% 为唯一分界线。**

### R2. §2 结果预览缺少「报告等级 + 一句话总结」，等级映射表整体缺失
- 业务需求梳理 §1.3 明确「考级结果概览 = 报告等级 + 成长区间 + 一句话总结 + 小提琴图」四件套，并给出完整映射表（0-30 待提升/初步形成 … 80-100 优秀/高阶表现）和四档总结文案。
- 方案概要 §3.1 的 §2 只写了「五档成长区间小提琴图 + 我的位置」，**报告等级（待提升/合格/良好/优秀）和一句话总结文案完全未出现**。
- 等级映射表是报告的判定中枢（连接分数→等级→成长区间→文案），方案层面必须占位，否则 PRD 无锚点。

### R3. 「无通过模块 → 不生成报告」边界未落地，且直接卡住入口设计
- 场景锚点 §3.1 明确该边界，但方案概要全文未提。
- 该边界不是纯后端规则——它直接决定 15_我的活动「查看报告」按钮的显示逻辑（全部未通过的考生：按钮隐藏？置灰？点击提示？）。
- mock 数据只覆盖场景 A（满分）/B（非满分），**缺少场景 C（全部未通过 → 无报告）**，入口交互无法闭环。

### R4. 报告入口描述与页面清单自相矛盾
- §3.2：「用户通过『我的活动』(15) **或『成绩与证书查询』(19)** 进入报告页」
- §5 涉及页面清单：只列了 15 的修改，**没有 19**。
- 二选一：要么 19 也加「查看报告」入口并列入清单，要么 §3.2 删掉 19。当前状态会让开发按两份不同范围执行。

### R5. 「题库建设」模块整体去向不明（范围缺口）
- 任务文件夹为「个人报告**与题库建设**」，业务需求梳理含 4 项题库需求：录题界面 AISE 题库/级别下拉（高）、题干上方「题目」字段（高）、题目列表筛选（中）、Python 参考答案上传（中）。
- 方案概要的本期范围只有报告页 + 知识标签管理，「本期不做的」清单也**只字未提这 4 项**。
- 若有意拆分为另一方案/另一期，必须在 §2 显式声明「题库建设由 XX 覆盖」；否则属需求遗漏。注意：题库「题目」字段、参考答案上传是报告 §4 展示的数据上游，分期顺序需要说明依赖关系。

## 🟡 建议优化

### O1. 等级判定逻辑未体现「最高通过模块对应等级」
方案 §1 顶部信息只写「获得级别（通过）OR 未通过说明」，未体现场景锚点 §3.1 的核心规则：任一模块未通过 → 显示**最高通过模块**对应等级。建议 §3.1 增加一行判定规则说明。同时补充通过判定标准（正式总分 <60 为未通过，业务需求 §1.2）。

### O2. 顶部信息缺「考试年月」字段
业务需求 §1.2 标题栏四字段：级别、学生姓名、**考试年月**、通过状态。方案 §1 漏了考试年月（如「2026年6月」）。

### O3. 掌握率公式两个版本需统一
业务需求梳理 §1.4.2：「得分之和 ÷ 满分值之和」（得分制）；场景锚点 §3.4：「做对题数 / 总题数」（题数制）。部分得分（编程题按用例给分）下两者结果不同，需确认采用得分制。

### O4. 知识点展示排序规则未提
业务需求 §1.4.3：先「重点提升」后「稳定掌握」，同状态内按知识树顺序。影响 §3 矩阵的渲染逻辑，建议补入方案。

### O5. §4 错题版缺三个关键细则
- 「客观题全对 → 仅展示编程题」分支（业务需求 §1.5.1）
- 编程题作答统一保留前 5 行截断（§1.5.2，影响 UI 高度设计）
- 两套点评文案（满分固定文案 / 非满分「建议重点提升【二级标签】」）
另建议 mock 增加「客观题全对」分支场景。

### O6. 知识标签管理右侧区域存在「两态」歧义
§4.1 架构图右侧是「知识点表格」（行=冒泡/二分实为三级标签），§4.4 又说「选中知识点后右侧显示三级标签」。需明确：选中模块时右侧显示知识点表格、选中知识点时切换为三级标签表格？顶部「新增模块/新增知识点」按钮与树选中态的联动（新增到哪个父节点）也需一句话定义。

### O7. 三级标签「全局唯一」约束过强，建议改为级别内唯一
业务现实是同名知识标签跨级别复用（如「while循环」在四、五级知识树都可能出现）。「同一标签不能出现在两个不同知识点下」会禁止这种复用。建议约束改为「**同一级别内唯一**」或「同一知识点内唯一」，并与运营确认。

### O8. 树形结构删除级联规则未定义
删除一级模块时其下知识点/标签如何处理（禁止删除非空节点 or 二次确认级联删除）？建议采用「非空节点禁止删除」的保守策略并写入方案。

### O9. 菜单命名统一
§4.2 侧边栏菜单项叫「知识标签」，页面标题是「知识标签管理」，建议统一为「知识标签管理」，与「标签配置」形成清晰区分。

### O10. 「查看报告」按钮显示条件需定义
15_我的活动卡片什么状态下显示该按钮（测评已完成且已出分？成绩公示后？）？与 R3 联动定义。修改时遵循现有卡片按钮视觉规范（references/设计约定-报名卡片展示规范.md）。
