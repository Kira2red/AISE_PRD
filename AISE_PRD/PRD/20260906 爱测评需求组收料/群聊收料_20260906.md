## 三、质量复盘：碎片化需求为什么质量不高

### 现象
一个周三晚上，群里同时滚动着 6 个话题（LXM 清单）+ 1 个研发求助（考场重名）+ 1 个 bug（证书Na）；周五上午同时有 3 个互不相干的需求在确认。需求以截图、口头、转发链接的形式流动，无文档、无编号、无验收口径，直接进开发。

### 原因
1. **收料无固定入口，群聊即需求**。需求散落在微信消息里，不归档就丢——本次 10 张截图归档时即挖出 6 项遗漏（含证书 Na 的关键线索、手机端适配顾虑、待澄清的考试 ID）。散的不仅是需求，还有上下文。

2. **规则空白被实现习惯填补，产品与研发两套方案并行**。典型：考场命名。PRD 没写命名规则 → 研发遇到重名自己起名（「[程序设计一级】9月3日 下午14:00-15:00」），产品侧同日另行拍板了「AISE｜测评名｜考场名｜4位码」——同一个问题两套方案，无人对齐。根因是 PRD 只写了「做什么」（自动创建考试），没写全「要素与边界」（名称是什么、超长怎么办、重名怎么办）。

3. **确认机制靠人肉催办**。祝星要在群里 @人 催「报告标题逻辑记得确定一下」，等级判定逻辑挂了数天无人闭环。缺一张全局待办台账，确认状态只存在于聊天记录里。

4. **bug 口头传递丢关键信息**。证书 Na 的「改成指定日期后合格字段生效、日期仍 Na」这条关键线索藏在长消息里，若无归档极易被消化成一句「日期显示有问题」。

5. **版本与发布纪律缺位**。iceping 样式错乱连 git 下载版本也错乱——demo/页面改动无版本说明、无发布核对，改错了无法定位是哪一版引入的。

### 改进机制
1. **固定收料通道**：群聊截图/消息 → 每次集中收料即归档进本台账（Hermes 可持续做），先归档再分流，杜绝「聊过就算提过」。
2. **需求准入门槛**：进开发前必须有「规则 + 边界 + 异常」三要素。规则空白的（如命名规则这类）先补 PRD；小需求用一句话卡片模板（背景/规则/验收），不因为「小」就免文档。
3. **规则变更当天对齐**：产品侧拍板的规则（如命名规则）当天同步执行群 @相关研发，消灭两套方案并行。
4. **全局台账周清**：各 PRD 改动日志的遗留事项缺少全局视图，本台账承担汇总角色，每周清一次：闭环的销项、新进的入表、超期的标红。
5. **bug 单独立项**：每条 bug 记录复现步骤 + 关键线索 + 怀疑方向（如证书 Na 的「规则切换未落库」），不靠口头传递。
6. **页面改动走版本纪律**：iceping/爱测评侧 demo 修改必须 git 提交 + 改动说明，样式错乱这类问题才能定位版本。
