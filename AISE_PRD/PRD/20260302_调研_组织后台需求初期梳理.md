# AISE 组织后台（B端接口对接与管理）需求初期梳理

基于系统目前的架构体系（用户端、管理端），现新增**组织后台（渠道/租户端）**，主要承载外部渠道开发者的工作台能力以及本渠道数据的查看与联测。整体需求涉及三个端的联动改造。

以下为初步梳理的影响范围和页面清单：

## 1. 管理端 (内部运营使用)
**改造目标：** 赋予内部运营创建渠道主体、并为其开通“组织后台”访问权限的能力。

*   **渠道管理功能扩充（基于现有“渠道管理”页面）：**
    *   **[改造] 渠道列表 (Table) 状态列与操作区：** 
        *   **新增列**：在现有的“创建时间”和“操作”列之间，新增一列**【组织后台状态】**，以不同颜色标签展示当前的开通及使用状态（如：`未开通`灰色、`正常`绿色、`已禁用`红色）。
        *   **操作列拆分**：当前操作列已有“编辑”（现改为**“编辑渠道”**，仅修改渠道本身的基础信息和关联活动）。新增**“编辑组织”**操作按钮。
    *   **[改造] 页面顶部搜索区：**
        *   在现有的“搜索渠道名称/ID”输入框旁边，新增一个下拉选择框：**【组织后台状态】**（选项包括：全部、正常、禁用、未开通）。
    *   **[新增] “编辑组织”综合管理大弹窗 (Modal)：** 
        *   这是一个包含多项组织后台配置项的大型表单弹窗，主要分为以下几个模块的内容：
        *   **1. 组织后台总体状态**：
            *   可以通过一个总开关或单选框全局启用/禁用该组织的后台登录与核心功能。
        *   **2. 组织管理员账号管理功能**：
            *   支持创建一个**系统默认管理员**以及多个**普通管理员**。
            *   **账号分配规则**：可为每一个管理员设置独立的登录账号和密码。账号在整个系统的所有组织内必须保证唯一，不可重复；密码支持管理员后续自行修改或重置。
            *   **权限与状态控制**：默认管理员拥有最高权限，不能被禁用；其他额外创建的普通管理员可被单独地【启用或禁用】。
        *   **3. API 能力与开发者凭证（凭据）管理功能**：
            *   **基本规则**：每个组织主体默认只分配**唯一的一组** `AppKey` 和 `AppSecret`，不支持创建多组不同的凭证。
            *   **重置与平滑过渡**：由于业务系统可能会在线上环境随时调用接口，直接销毁旧秘钥会导致接口瞬间全部报错。因此需要提供**【重置并平滑过渡】**的功能。
                *   当点击“重置密钥”时，系统**生成并下发一个新的 `AppSecret`**。
                *   此时原有的旧 `AppSecret` **保留一段过渡期**（比如 2 小时 或者运营手动设置的 1~3 天），在此期间内，新、旧两个 Secret 都可以成功调用鉴权。
                *   过渡期结束后，旧的 Secret 自动作废失效。同时需要配合在组织后台的“重置日志/弹窗”中，醒目提示开发者过渡期剩余时间倒计时。
            *   提供一个独立的启停开关，用于单独**【启用/禁用 API 调用能力】**（禁用后无论密钥是否正确，所有调用直接返回拦截错误，可适用某些只需机构登录后台看板数据，但不允许通过接口推送报名的业务场景）。
    *   **报名记录管理功能扩充：**
        *   **[改造] 报名列表 (Table) 及右侧详情抽屉：**
            *   在列表中新增**【支付方式】**字段（区分于现有的“渠道来源”）。该字段用于明确当前订单是如何付款的，例如：“微信支付（C端线上支付）”、“平台免单”、“B端代付/后付费签单”等。
            *   在右侧的【订单详情抽屉】内，同步增加展示“支付方式”及对应的支付单号或关联凭证流水号信息。
        *   **[改造] 页面顶部搜索区：**
            *   新增一个下拉筛选框：**【支付方式】**，以便运营人员进行财务对账或按支付方式导出报表。

## 2. 组织后台 (全新端 - 面向渠道/B端客户的管理员或开发者)
**改造目标（第一期）：** 提供给B端机构独立使用的后台，聚焦于开发者对接联调、接口配置及自身渠道基础业务数据的查询。第一期仅包含以下核心功能：

*   **1. 登录与基础架构：**
    *   **[新增] 登录页：** 提供给组织后台管理员的独立登录入口（基于管理端创建分配的账号密码）。
*   **2. 开发者管理模块：**
    *   **[新增] 凭证配置页 (密钥管理)：** 供渠道开发者查看分配的 API 鉴权信息（`AppKey`, `AppSecret`）。可以进行 `AppSecret` 的重置操作（带剩余有效期的平滑过渡重置）。
    *   **[新增] Webhook 事件订阅页：** 供渠道开发者配置用于接收数据回调的 `callback_url`，并可按需勾选需要订阅的事件分类（如订单状态、测评进度、成绩下发等）。
    *   **[新增] 联调与日志排查页：** 展示 API 请求日志以及 Webhook 推送回调记录，便于机构开发人员自行排查对接 BUG（如查看 400/500 报错报文 payload、支持接口重试等）。
*   **3. 业务管理模块 (核心数据落地)：**
    *   **[新增] 学生列表**：根据原始 PDF **数据字典（第3章）** 呈现通过预报名 API 推送成功的本渠道用户。
        *   **【顶部筛选器】**：姓名、手机号、证件号，支持精准/模糊查询。
        *   **【列表页高优展示字段】**：`name` (姓名)、`telephone` (手机号：唯一索引)、`identity_type` (证件类型)、`identity` (证件号码)、`status` (数据写入状态：待写入/写入失败/写入成功)、入库时间。
        *   **【学生详情页（侧滑/弹窗）】**：展示收集的所有字段。除了上述高优字段外，还需展示：`sex` (性别)、`name01` (紧急联系人)、`telephone01` (紧急联系电话)、`school` (就读学校)、`pic_url` (准考证照片)、完整的证书邮寄地址（省 `province`/市 `city`/区 `area`/街 `street`/详细地址 `post_address`）及收件人信息（`post_man`, `post_phone`）。
    *   **[新增] 报名列表**：按照所选的测评活动，展示该渠道学生的每一次测评报名记录及最终考试结果。
        *   **【表头字段体系】**：（与内部管理端的“报名管理”严格保持一致并简化敏感金额）**报名信息（含报名号/活动名）**、**考生信息（含头像/姓名/手机号）**、**支付状态**、**【测评进度】**、**成绩得分**、**报名时间**。
        *   **【顶部筛选器】**：测评活动（核心下拉框，作为查询前置）、搜索订单号/姓名/手机号、支付状态、测评进度状态。
        *   **【测评进度与状态映射规则】**：这里的状态完全遵循 PDF 第四章 **Webhook 回调事件（业务进度）** 节点：
            *   *当接收到* `PAYMENT_SUCCESS` *(支付成功) 后，对应记录的“支付状态”列更新为**【已支付】**。*
            *   `STATUS_1_PENDING` (待测评：用户未登录)
            *   `STATUS_2_WAITING` (候考中：已登录、检录中)
            *   `STATUS_3_TESTING` (测评中：考场答题)
            *   `STATUS_4_FINISHED` (已测评：完成交卷)
            *   `STATUS_5_ABSENT` (确定缺考)
            *   *当接收到* `RESULT_SCORE` *后，对应记录的“成绩得分”列更新实际分数。*
            *   *当接收到* `RESULT_CERT` *后，在操作列提供“查看证书”或状态变更为“证书已生成”。*

## 3. 用户端 (学生/家长使用 - 一期无改造需求)
**改造目标：**
在第一期且暂不考虑免密 SSO（单点登录）等深度集成的场景下，用户端**保持现有逻辑，无需进行任何改造**。
所有通过 API 推送预报名的渠道学生数据，在用户端表现为正常的已有账号（或静默落库），用户通过标准流程使用账号密码（或手机号验证码）正常登录并完成原有支付、答题流程即可。相关的渠道流水号等数据由后端处理。
